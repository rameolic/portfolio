Project overview

InsightsE Canteen is a Flutter desktop POS used in school canteen environments. It supports wallet-based transactions and connects to broader education-management operations through backend APIs. I independently designed, developed, and delivered the production application in one month—owning architecture through release.

NFC/RFID integration

The desktop application supports NFC/RFID-based identification as part of payment-related canteen workflows. Scanning identifies the relevant wallet/user context so staff can complete transactions quickly at the point of sale without relying on slow manual lookup paths.

Integration work focused on reliable read handling in a desktop environment and wiring identification events into the transaction flow managed by application state.

Thermal receipt printing

After a transaction completes, the POS generates a thermal receipt through an integrated printer workflow. The desktop client formats transaction details for receipt output so canteen staff can provide an immediate printed record.

Offline transaction queue

Connectivity in canteen environments can be intermittent. The application supports an offline-capable transaction workflow:

  1. A transaction is initiated at the POS.
  2. The application handles the transaction through its offline-capable workflow.
  3. Transaction information is queued when connectivity is unavailable.
  4. Pending transactions are synchronized when connectivity returns.
  5. Backend acknowledgments help confirm synchronization.
  6. Unique transaction identifiers support duplicate prevention.

This design prioritizes operational continuity during network interruptions. It does not claim a specific storage engine, Redis configuration, or a guarantee of zero transaction loss.

ERPNext API integration

The POS communicates with ERPNext backend APIs for transaction-related operations used by the wider system. My ownership was the Flutter desktop client integration—request/response handling, acknowledgment flows, and aligning client behavior with backend confirmation—not development of the ERPNext backend itself.

The compressed timeline required decisive architecture choices, ruthless scope focus, and end-to-end ownership—from UI and state management through hardware integrations and production readiness.
